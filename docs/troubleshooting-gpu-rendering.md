# GPU 렌더링 병목 문제 해결 사례

> CARLA 시뮬레이터 카메라 센서가 비정상적으로 느린 원인을 규명하고 55.5배 성능 개선을 달성한 과정

## 문제 상황

LMDrive(Vision-Language-Action 자율주행 모델) 베이스라인 평가를 진행하던 중, 시뮬레이션이 정상 속도의 수백 분의 1로 동작하는 문제가 발생했다.

- 에이전트 시간 1초 = 실제 시간 약 10분
- 16개 시나리오 평가에 약 80시간 소요 예상
- 연구 진행이 사실상 불가능한 수준

## 초기 가설과 검증

### 가설 1: GPU 성능 부족

nvidia-smi로 확인한 결과 GPU 사용률이 0~2%에 불과했다. GPU가 병목이라면 사용률이 높아야 하므로 이 가설은 기각했다.

### 가설 2: LLM 추론 속도 한계

LLaVA 7B 모델의 추론이 느려서일 것으로 추정했으나, 단순 GPU 연산 테스트에서 0.02초/10회로 정상 속도가 확인되어 기각했다.

### 가설 3: CARLA 시뮬레이터 자체의 성능 문제

CPU 사용률이 1200%까지 치솟는 현상을 발견했다. 조사 결과 CARLA 0.9.15의 동기 모드 busy-wait 버그(GitHub Issue 9250)로 확인되었으나, 이는 네이티브 Linux에서도 동일하게 발생하는 문제로 근본 원인은 아니었다.

## 원인 규명: 변인 통제를 통한 단계적 격리

전체 파이프라인을 구성 요소별로 분해하여 각각의 소요 시간을 독립적으로 측정했다.

| 테스트 조건 | 20틱 소요시간 |
|---|---|
| CARLA 순수 tick (센서 없음) | 0.32초 |
| LiDAR 센서만 부착 | 0.60초 |
| RGB 카메라 부착 (800x600) | 17.97초 |
| RGB 카메라 부착 (200x150) | 14.74초 |

**핵심 발견 1**: 카메라 센서만 56배 느렸다. LiDAR는 정상 속도였다.

**핵심 발견 2**: 해상도를 16분의 1로 줄여도 개선이 미미했다(17.97초에서 14.74초). 즉 데이터 양이 아니라 렌더링 경로 자체의 문제였다.

LiDAR는 레이캐스팅 연산만 수행하고 GPU 렌더링이 불필요한 반면, RGB 카메라는 3D 장면을 실시간 렌더링해야 한다는 차이에 주목하여 그래픽 드라이버를 점검했다.

glxinfo 결과:
llvmpipe는 Mesa의 CPU 소프트웨어 렌더러다. NVIDIA GPU가 있음에도 GPU 렌더링이 전혀 사용되지 않고 24코어 CPU가 픽셀을 일일이 계산하고 있었다.

추가 확인 결과, Vulkan 역시 동일하게 llvmpipe로 폴백되고 있었으며, 시스템에 NVIDIA용 그래픽 드라이버 파일이 존재하지 않았다.

- /usr/share/vulkan/icd.d/ 에 nvidia_icd.json 없음 (intel, radeon, nouveau 등만 존재)
- libGLX_nvidia.so 파일 시스템 전체 검색 결과 없음
- 반면 /usr/lib/wsl/lib/ 에는 CUDA 연산용 라이브러리(libnvidia-ml, libnvidia-encode 등)만 존재

## 진단 결론

**GPU 연산(CUDA)과 GPU 렌더링(Vulkan/OpenGL)은 서로 다른 드라이버 경로를 사용한다.**

WSL2 환경에서 NVIDIA 드라이버는 CUDA 경로만 패스스루하고, 그래픽 렌더링 경로는 제공하지 않고 있었다. PyTorch는 정상 동작했기 때문에 "GPU가 잘 작동한다"고 오판하기 쉬운 상황이었다.

이것이 사용자 설정 오류가 아님을 검증하기 위해 외부 사례를 조사한 결과, NVIDIA 개발자 포럼에서 동일한 GPU(RTX 5070 Ti) 및 동일한 드라이버 버전(591.86)으로 같은 증상을 겪은 보고를 확인했다. RTX 50 시리즈(Blackwell 아키텍처)와 WSL2 조합에서 그래픽 드라이버 패스스루가 미지원 상태인 알려진 문제였다.

## 해결 및 검증

환경 설정으로 해결 불가능한 드라이버 레벨 문제로 판단하여 네이티브 Ubuntu 듀얼부팅으로 전환했다. 전환 전 작업 환경 재현성 확보를 위해 conda 환경 명세와 수정 코드 일체를 백업했다.

전환 후 동일한 조건으로 재측정한 결과:
| 환경 | 카메라 20틱 소요시간 |
|---|---|
| WSL2 | 17.97초 |
| 네이티브 Ubuntu | 0.32초 |

**55.5배 개선**되었으며, 이 수치는 센서를 전혀 부착하지 않은 순수 tick 속도(0.32초)와 동일하다. 즉 카메라 렌더링으로 인한 오버헤드가 사실상 제거되었음을 의미한다.

## 회고

이 문제의 난점은 표면적 증상이 원인을 가리고 있었다는 점이다. nvidia-smi에서 GPU가 정상 인식되고 PyTorch의 torch.cuda.is_available()이 True를 반환했기 때문에, GPU 관련 문제라고는 전혀 의심하지 않았다.

해결의 전환점은 "카메라와 LiDAR의 차이가 무엇인가"라는 질문이었다. 두 센서 모두 CARLA의 센서 API를 사용하지만, 카메라만 GPU 렌더링 파이프라인을 경유한다는 구조적 차이를 인지하면서 문제의 범위를 그래픽 드라이버로 좁힐 수 있었다.

또한 해상도를 변경해도 개선되지 않는다는 실험 결과가 "데이터 처리량 문제"라는 오답을 배제하는 데 결정적이었다. 변인을 하나씩 통제하며 측정하는 접근이 없었다면 하드웨어 업그레이드나 모델 경량화 같은 잘못된 방향으로 시간을 소모했을 가능성이 높다.

## 환경 정보

- GPU: NVIDIA GeForce RTX 5070 Ti (Blackwell, sm_120)
- Driver: 591.86 / CUDA 13.1
- 시뮬레이터: CARLA 0.9.15
- 전환 전: WSL2 (Ubuntu 26.04)
- 전환 후: Ubuntu 26.04.1 LTS (네이티브)
